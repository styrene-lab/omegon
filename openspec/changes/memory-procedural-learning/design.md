# Procedural learning design

Depend on evidence capture, reconciliation, and shared selection. Memory owns
experience records and procedural candidates. `omegon-skills` owns portable skill
parsing/validation and activation policy. The main crate composes promotion and
status operations through registered semantic surfaces. Read local skills-crate
directives before implementation.

A procedural candidate records task class, prerequisites, applicability, ordered
steps or source references, expected outcome, validation, failure conditions, and
supporting/counterexample episode IDs. Keep hypotheses distinct from verified
workflow evidence. One successful run does not establish universal applicability.

Selection retrieves applicable procedures alongside facts under the same context
budget. Execution remains governed by the user's task and existing tool authority.
Procedural text cannot grant capabilities or bypass runtime checks.

Link actual execution feedback to the selected procedure/version and evidence.
Successful retrieval is not successful application. Counterexamples can narrow
applicability, flag a hypothesis, or propose a replacement through reconciliation.
Measure repeated-error avoidance and task success in the evaluation corpus.

Promotion is an explicit operation that renders and validates an artifact with the
existing skill format and preserves source evidence. Compare target versions before
writing. Do not silently overwrite a human-authored skill. Define the concrete
promotion command/API in the existing registry during implementation, not a new
standalone runtime. Automatic candidate creation does not imply automatic promotion.
