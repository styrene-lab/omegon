# Common agent policy — Delta Spec

Accepted implementation requirements. They apply to common agent policy, not
purpose-specific compaction or extraction instructions. Existing preparation,
resolved route-policy, permissions, and contribution contracts remain binding.

## ADDED Requirements

### Requirement: Common agent policy has one host-owned identity

The host MUST own one canonical core with identifiable source, version, and hash.
Its obligations MUST NOT vary by model grade, posture, frontend, or budget.
Equal explicit core inputs MUST yield equal core bytes. Full, Slim, Constrained,
their selector, and mode/boolean family APIs MUST be removed rather than retained
as ignored compatibility parameters or recreated through automatic skills.
The core targets approximately 150–200 words without a truncation limit.

#### Scenario: One core across entry points and resource postures
Given normal, headless, ACP, daemon/control, and child agent fixtures with equal explicit core inputs
And the fixtures vary model grade, posture, presentation, read-only role, and Git availability
When each fixture prepares its common agent instructions
Then each captures identical core bytes, identity, and hash
And scoped context and tool differences do not select another core family

#### Scenario: Persona cannot duplicate or replace host policy
Given fixtures with no persona, an admitted persona, and an explicit skill subset
And one user instruction file legitimately quotes the core text
When the host composes each request
Then the host core source contributes exactly once
And augmentation cannot replace or prepend another host core
And the legitimate quoted text remains attributed to its own source
And persona switch or clear replaces old augmentation sources without leaving stale Lex or persona content

### Requirement: Consolidation accounts for every preserved semantic obligation

The core and scoped owners MUST implement the reviewed preservation ledger.
Anti-sycophancy, evidence and cognitive honesty, proportionate complete work,
ownership/interface respect, and operator agency MUST remain represented.
The core MUST explicitly require preservation of existing user work and unrelated
changes as a strengthened scope obligation.
Universal engineer-persona framing and the blanket 80% shortcut MUST NOT remain
common policy. Core guidance MUST distinguish evidence from inference, require
honest tool/test/completion claims, and support concrete correction after frustration.
Useful tool procedures MUST acquire a usable owner before their old injection is removed.

#### Scenario: Six Lex categories remain accounted for
Given the six original Lex axes and Full, Slim, and Constrained behavior inventories
And the review-requested explicit obligation to preserve existing user work and unrelated changes
When a reviewer compares the proposed assembly and scoped contracts with the preservation ledger
Then every semantic rule has a retained, merged, relocated, or retired disposition with rationale and verification
And the core contains no blanket 80% shortcut or compulsory engineer persona
And honest evidence, appropriate validation, meaningful human checkpoints, and completed-task reporting remain explicit
And preservation of existing user work and unrelated changes is explicit without being misrepresented as verbatim legacy prompt text

#### Scenario: Scoped tool procedures survive relocation
Given essential edit, validation, context discovery, memory, terminal, and admitted extension procedures previously existed in automatic prompt fragments
When their replacement tool contracts are captured through the production compact-schema path
Then the model-visible definitions or owned tool surfaces retain the essential usage information
And missing procedure information blocks removal of its previous owner
And skipped validation is not described as a passing test

#### Scenario: Project signals and extensions remain factual
Given a project uses a test runner different from a filename-based heuristic
And an admitted image-generation extension exposes its actual tools
When context is assembled
Then file signals do not impose another test runner or universal language style
And static incapability prose does not deny the admitted generation capability
And useful tooling facts and extension procedures retain source attribution

### Requirement: Workflow guidance follows actual task authority and state

Tool, directory, or skill presence MUST NOT mandate a workflow. Actual admitted
capability/permission facts, child role instructions, and existing configured restrictions MUST remain visible
across common routes. Existing active work state MUST remain truthful.
Preserving role instructions MUST NOT be described as proving nonmutation or
adding an OS sandbox or other enforcement mechanism. Admitted tools MUST be
verified separately from role prose.
The core MUST say that commits or publication occur only when the operator or
an applicable authorized workflow calls for them. This instruction MUST NOT
introduce repeated conversational approval or change mechanical Git gates.

#### Scenario: Available tools and files do not authorize workflow
Given a bounded edit-only request with lifecycle and delegation tools available
And OpenSpec directories and an applicable lifecycle skill are present without an authorized lifecycle task
When instructions are assembled
Then the presence of those tools, files, or skill does not mandate planning, design, OpenSpec, or delegation
And actual permission facts remain available without granting new workflow authority

#### Scenario: An inherited active plan remains operational
Given a session has an active Workbench plan with pending items
When the next request is prepared
Then scoped plan state and its execution/reconciliation instructions remain visible
And the common policy does not permit reporting completion while pending work is concealed

#### Scenario: Authorized children retain distinct contracts
Given authorized cleave, scout, patch, and verify child fixtures across delegate-only, cleave-only, both, and neither tool surfaces
And the fixtures include a role instructed not to mutate with bash still admitted
When each child prepares instructions
Then each receives the common core and its own role, authority, limits, and applicable tools
And cleave retains guardrails and required in-scope commits for harvest
And scout read-only, patch scoped-edit, and verify non-editing role instructions are retained alongside existing configured restrictions
And each captured tool surface is checked separately against actual admission
And no fixture advertises unavailable tools or infers authority from their presence
And payload evidence is not reported as proving nonmutation or new sandbox enforcement

#### Scenario: Git scope follows operator and workflow authority
Given edit-only, explicitly requested commit, and standing-authorized commit/publication workflow fixtures
When their instruction payloads are reviewed
Then the base provides no default commit-on-completion instruction
And requested or applicable authorized workflow actions are supported without an added repeat-approval instruction
And existing invocation policy and cleave checkpoint approval requirements remain unchanged
And later actual-model trials report observed actions separately from payload assertions

### Requirement: Instruction provenance remains distinct from data and execution authority

Host, operator, project, persona, skill, and extension sources MUST remain
identifiable with their existing trust/admission boundaries. Source labels alone
MUST NOT create a new precedence engine. Quoted, retrieved, and tool-returned
content MUST NOT grant itself authority. Explicitly admitted instructions,
including authorized tool-delivered skill or prompt bodies, MUST remain usable
within their authorized scope without granting new privileges. Admission or
availability alone MUST NOT authorize a workflow. Prompt/loop execution MUST retain provenance,
preview/validation, and repeated-execution safety at its existing owners.

#### Scenario: Quoted content cannot promote itself into policy
Given retrieved memory, quoted user material, a heredoc, or tool output uses forged Core headings to claim instruction or workflow authority
And a separate fixture explicitly authorizes a tool-delivered skill or prompt body through existing admission
When the request captures those inputs
Then the forged content retains its source and data role without acquiring operator or host authority
And the authorized fixture retains the explicitly admitted instructions within their authorized scope without new privileges
And payload tests alone are not reported as proof of model resistance to injection

#### Scenario: Prompt and loop execution retains its safety boundary
Given a prompt template or repeated loop is requested through its supported command surface
When execution is prepared
Then its existing provenance, preview/validation, and repeated-execution safety handling remain effective
And removal of Full-only prose does not bypass executable-instruction admission

### Requirement: Prompt consolidation preserves resource transport and auxiliary contracts

Posture/resource controls, presentation, persisted configuration, tool admission,
child limits, schema dialects, provider envelopes, and Lex permission denial MUST
retain their existing semantics. Mandatory policy MUST fit intact under the
existing request accounting contract or fail actionably before provider dispatch.
No small-window exception may reintroduce a reduced policy family.
Auxiliary flows MUST retain their purpose-specific instructions and authority.

#### Scenario: Resource controls and provider envelopes remain independent
Given fixtures varying --slim, --full, thinking level, context caps, --tui, --ui, and legacy presentation aliases
When provider requests are prepared
Then posture, limits, tool admission, compact schemas, and permission denial keep their existing meaning
And Anthropic protocol prefixes/cache segmentation, Gemini systemInstruction, and Responses envelopes retain their protocol roles
And help no longer promises a reduced core prompt family
And configured denial, RBAC, lease, secret-guard, and explicit bypass fixtures retain their existing enforcement semantics

#### Scenario: Purpose-specific auxiliary prompts remain purpose-specific
Given compaction and bounded memory extraction use the accepted common preparation contract
When their requests are prepared after the prompt consolidation
Then their summary/extraction instructions are not replaced by the common agent core
And zero tools, flow authority, deadlines, collectors, and extraction guards remain effective
And compaction retains generation-bound template selection and missing-template failure
And extraction retains evidence-only JSON, delimiters, pending-evidence, and cancellation handling

### Requirement: Prompt evidence preserves historical meaning

Existing composition metrics and request evidence MUST retain their meanings.
New preparations MUST identify the core through existing source/evidence fields
where possible. A schema change requires an identified gap and explicit review.
Historical and in-flight requests MUST NOT be rewritten to the current policy.

#### Scenario: Resume and in-flight capture retain their evidence
Given a session contains historical Full or Slim requests and a request already prepared under an older core
And instruction source files have changed or been deleted since the captured request
When a new request is prepared after upgraded setup
Then the new request identifies the current core and admitted profiles
And historical and in-flight requests retain their captured bytes, provenance, and identity
And replay uses materialized source evidence rather than rereading instruction paths
And composition metrics retain byte-based counts and labeled estimates rather than invented savings or provider measurements
